Java Architecture & Code Execution

Java platform fundamentals — JDK, JRE, JVM, core language concepts — plus a complete walkthrough of what happens from writing Main.java to JVM termination.

Java Platform Architecture

Java is not just a language — it is a platform made of tools, libraries, and a runtime that work together. Understanding this stack is the foundation for everything else in these notes.

JAVA PLATFORM ┌─────────────────────────────────────────┐ │ JDK (Development) │ │ ┌───────────────────────────────────┐ │ │ │ Development Tools │ │ │ │ javac, jar, javadoc, jshell, ... │ │ │ └───────────────────────────────────┘ │ │ ┌───────────────────────────────────┐ │ │ │ JRE (Runtime) │ │ │ │ ┌─────────────────────────────┐ │ │ │ │ │ JVM │ │ │ │ │ │ Class Loader, GC, JIT, ... │ │ │ │ │ └─────────────────────────────┘ │ │ │ │ Core Libraries (java.lang, │ │ │ │ java.util, java.io, ...) │ │ │ └───────────────────────────────────┘ │ └─────────────────────────────────────────┘

JDK — Java Development Kit

  • Everything you need to write and build Java programs
  • Includes javac (compiler), debugger tools, and documentation generators
  • Contains the JRE inside it
  • Installed on your machine when you develop Java

JRE — Java Runtime Environment

  • Everything needed to run Java programs (no compiler)
  • JVM + standard class libraries
  • End users who only run apps need a runtime, not the full JDK
  • Modern JDK distributions bundle runtime; a separate JRE install is less common today

JVM — Java Virtual Machine

The heart of Java execution. The JVM is a virtual computer that reads bytecode and runs it on real hardware.

  • Class Loader — loads .class files into memory
  • Bytecode Verifier — checks bytecode is safe and valid
  • Execution Engine — interpreter + JIT compiler
  • Garbage Collector — automatically frees unused objects
  • Native Interface (JNI) — talks to OS and native libraries

Write Once, Run Anywhere (WORA)

Java source compiles to platform-neutral bytecode. The same Main.class file can run on Windows, Linux, or macOS — as long as a JVM exists for that OS and CPU architecture.

Main.java ──javac──▶ Main.class (same everywhere) │ ┌───────────────┼───────────────┐ ▼ ▼ ▼ JVM (Windows) JVM (Linux) JVM (macOS) │ │ │ ▼ ▼ ▼ x86-64 ARM64 x86-64 machine code machine code machine code
Compiled + Interpreted Java is compiled to bytecode at build time (javac) and interpreted/JIT-compiled at runtime (JVM). This hybrid model gives portability and performance.

Java Language Basics

Before diving into execution details, here are the core building blocks every Java program uses.

Program Structure

Every Java application is organized into classes. Execution starts from a class that contains a main method.

package com.example;          // optional — groups related classes

import java.util.List;         // optional — use classes from other packages

public class Main {            // class name must match filename: Main.java
    public static void main(String[] args) {
        // entry point — JVM calls this first
    }
}

Class

A blueprint that defines fields (data) and methods (behavior). In OOP, you create objects from classes.

main() method

public static void main(String[] args) — must be public, static, return void, and accept a String[]. The JVM searches for this signature to start the program.

Four Pillars of OOP (Object-Oriented Programming)

ConceptMeaning in Java
EncapsulationHide internal state with private fields; expose via public methods
InheritanceA class extends another (class Dog extends Animal) and reuses its behavior
PolymorphismSame method name, different behavior — method overriding and interfaces
AbstractionHide complexity — abstract classes and interfaces define what, not how

Static vs Instance

static members

  • Belong to the class, not any single object
  • One copy shared by all instances
  • main() is static — JVM calls it without creating an object first
  • Static blocks run once during class initialization

instance members

  • Belong to a specific object
  • Each object has its own copy of instance fields
  • Need new ClassName() before calling instance methods
  • Non-static methods receive implicit this reference

Primitive vs Reference Types

PrimitivesReference Types
byte, short, int, long, float, double, char, booleanClasses, arrays, interfaces, enums
Store actual values directlyStore a reference (address) to an object on the heap
Live in stack frames (local vars) or inside objectsObject data lives on the heap; variable holds a pointer

Access Modifiers

ModifierVisibility

Packages

Packages organize classes into namespaces and prevent naming conflicts. The folder structure usually mirrors the package: com.example.Main → com/example/Main.java.

Convention Package names are lowercase (e.g. java.util, com.myapp.service). Class names use PascalCase (ArrayList, HashMap).

JVM Memory Areas

When the JVM runs your program, it divides memory into distinct regions. This connects directly to stack frames, objects, and garbage collection covered later.

JVM RUNTIME DATA AREAS ┌──────────────────────────────────────────────────┐ │ Method Area (Metaspace) │ │ Class metadata, static variables, constant pool │ ├──────────────────────────────────────────────────┤ │ Heap (shared — all threads) │ │ Objects, arrays — managed by Garbage Collector │ ├──────────────┬───────────────────────────────────┤ │ Per Thread │ │ │ ┌─────────┐ │ │ │ │ Stack │ │ Stack Frames (local vars, │ │ │ │ │ operand stack per method call) │ │ ├─────────┤ │ │ │ │ PC Reg │ │ Points to current bytecode insn │ │ ├─────────┤ │ │ │ │ Native │ │ For JNI / native method calls │ │ │ Stack │ │ │ │ └─────────┘ │ │ └──────────────┴───────────────────────────────────┘

Heap

All new objects and arrays live here. Shared across threads. The Garbage Collector reclaims objects with no references. Divided into Young Gen (Eden + Survivor) and Old Gen in most JVMs.

Stack (per thread)

Each method call pushes a stack frame with local variables and an operand stack. When the method returns, the frame is popped. Primitives and references (pointers to heap objects) are stored in local slots.

Method Area / Metaspace

Stores class-level data: bytecode, method tables, static fields (like static int x = 100), and runtime constant pool. In modern JVMs this is called Metaspace (native memory, not the Java heap).

PC Register & Native Stack

PC Register — tracks which bytecode instruction is executing. Native Method Stack — used when Java calls native (C/C++) code via JNI.

Stack vs Heap — quick rule Local variables and method calls → Stack. Objects created with new → Heap. Static class data → Method Area.

Example Mapping

For our sample program:

  • static int x = 100 → Method Area (class data)
  • int a = 10 in main() → Stack frame local variable slot
  • String objects from println → Heap (if allocated)
  • main() and add() frames → Thread stack (push/pop on calls)

Example Code

We use this program throughout the notes:

public class Main {

    static int x = 100;

    static {
        System.out.println("Static block executed");
    }

    public static void main(String[] args) {
        int a = 10;
        int b = 20;

        int sum = add(a, b);

        System.out.println(sum);
    }

    public static int add(int x, int y) {
        return x + y;
    }
}

1 Write Code

You write Java code in a text file: Main.java. This is called Java source code.

int a = 10;
int b = 20;

At this point the file contains human-readable instructions, but the CPU cannot directly understand Java syntax. The CPU understands machine instructions, so source code must be processed first.

Main.java ↓ Compiler

2 Compile — javac Main.java

javac is the Java compiler. It processes your source code in several stages:

Main.java │ ▼ Lexical Analysis │ ▼ Syntax Analysis │ ▼ Semantic Analysis │ ▼ Bytecode Generation │ ▼ Main.class

2.1 Lexical Analysis

The compiler reads characters and breaks them into meaningful units called tokens.

int a = 10;
TokenType
intKeyword
aIdentifier
=Assignment operator
10Integer literal
;Separator
Characters → Tokens

2.2 Syntax Analysis

The compiler checks whether tokens follow Java grammar rules.

Valid

int a = 10;

Invalid

int = a 10;

Conceptually, the compiler builds an Abstract Syntax Tree (AST):

Variable Declaration │ ├── Type → int ├── Variable → sum │ └── Method Call ├── Method → add ├── Argument → a └── Argument → b

2.3 Semantic Analysis

Checks whether the program makes sense according to Java rules.

Type mismatch example int a = 10; String name = a; — syntax is valid, but types are incompatible.

For int sum = add(a, b); the compiler checks:

  • Does add() exist?
  • Does it accept two arguments?
  • Are a and b valid arguments?
  • Does add() return an int?
  • Can the result be stored in sum?

Other checks: type checking, variable existence, method existence, access modifiers, inheritance, exceptions.

Compile-time Error If something is wrong, no successfully compiled program is produced.

2.4 Bytecode Generation

If everything is valid, the compiler generates Main.class containing Java bytecode.

Main.java │ javac ▼ Main.class

Bytecode is an intermediate format — not source code, not native CPU code. It is designed to be executed by the JVM.

$ javap -c Main

3 Run — java Main

javac Main.java

  • Compiles source code
  • Creates Main.class

java Main

  • Starts the Java runtime / JVM
  • Executes the Main class

The OS starts a Java process. The JVM does not send the entire .class file directly to the CPU — classes must be loaded and prepared first.

4 JVM Starts

The JVM is responsible for running Java bytecode. It is the runtime component of the Java platform (see Java Architecture) — it allocates memory areas (see JVM Memory Areas) and begins loading your entry class.

Operating System │ ▼ Java Process │ ▼ JVM ├── Loads Classes ├── Manages Memory ├── Executes Bytecode ├── Performs JIT Compilation └── Performs Garbage Collection

The JVM now needs to execute your Main class → class loading.

5 Class Loading

Class │ ▼ Loading │ ▼ Linking ├── Verification ├── Preparation └── Resolution │ ▼ Initialization

5.1 Loading

The Class Loader locates and reads Main.class:

Disk: Main.class │ ▼ Class Loader │ ▼ Class information available to JVM

The JVM obtains:

  • Class Name: Main
  • Methods: main(), add()
  • Fields: static int x
  • Superclass: Object

For System.out.println(sum), Java also needs System and PrintStream. Classes load as they become necessary.

5.2 Linking

A. Verification

The JVM checks bytecode is valid and safe:

  • Valid structure?
  • Valid instructions?
  • Correct type usage?
  • Valid stack operations?

B. Preparation

Prepares storage for static int x = 100. Actual assignment happens during initialization.

C. Resolution

Connects symbolic references (add, System.out.println) to actual runtime targets.

5.3 Initialization

Static fields and blocks run in source-defined order:

Class Initialization │ ▼ static int x = 100 │ ▼ static block │ ▼ "Static block executed" │ ▼ main()
Important Output begins with Static block executed before anything inside main() runs.
JVM starts ↓ Class loading / linking ↓ Class initialization (static fields + blocks) ↓ main()

9 Execution Engine

Execution Engine ├── Interpreter └── JIT Compiler

9.1 Interpreter

Executes bytecode instructions one by one. Useful when code first runs, but repeatedly interpreting the same code adds overhead.

9.2 JIT Compiler

Just-In-Time Compiler — detects frequently executed ("hot") code paths:

Bytecode │ ▼ Interpreter starts │ ▼ Code becomes hot │ ▼ JIT Compiler │ ▼ Native Machine Code │ ▼ Optimized execution
Key insight Java does not always interpret forever. The JVM compiles important hot code into native machine code for faster execution.

10 Native Machine Code

The CPU cannot execute bytecode directly. Operations must use processor instructions.

Java Source → Bytecode → JVM ├── Interpreter └── JIT → Native Machine Instructions → CPU

Different architectures (x86-64, ARM64) have different instruction sets. Bytecode portability lets the same .class run on JVMs for different platforms.

CPU Execution & Output

For System.out.println(sum);:

System → out → PrintStream → println(sum) │ ▼ Standard Output → OS / Terminal → Screen

The user sees: 30

Java statement ↓ Bytecode operation ↓ JVM execution ↓ Java library methods ↓ OS output facilities ↓ Terminal → 30

11 main() Finishes

After the last statement, main() returns and its stack frame is removed.

main() completes │ ▼ main() stack frame removed │ ▼ Main thread finishes

JVM Terminates

main() finishes │ ▼ Non-daemon threads still running? │ ┌───┴───┐ Yes No │ │ ▼ ▼ JVM keeps JVM running terminates

Normally: main() finishes → non-daemon threads finish → JVM shuts down.

Quick Revision

Architecture: JDK = dev tools + JRE. JRE = JVM + libraries. JVM = virtual machine that runs bytecode with class loading, memory management, and GC.

Basics: Programs are classes; main() is the entry point. Objects live on the heap; method calls use the stack; static data lives in the method area.

Execution: Java source is compiled by javac into bytecode; the JVM loads and prepares required classes, initializes them, creates stack frames to execute methods, uses the interpreter and JIT compiler to run bytecode as native instructions, sends results to the CPU and output system, and terminates when non-daemon threads have finished.
